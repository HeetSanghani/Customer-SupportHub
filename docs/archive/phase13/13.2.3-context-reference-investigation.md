# Phase 13.2.3 — Contextual Reference Resolution Investigation

## Executive Summary

**Investigation Status**: `ROOT_CAUSE_IDENTIFIED`

Phase 13.2.3 conducted a strict read-only diagnostic investigation into a new manual validation failure discovered after the Phase 13.2.2 context isolation remediation.

The failure is:

> Turn 1: `"Tell me about PROD-002."` → Product PROD-002 ✅  
> Turn 2: `"What is its price?"` → **Order ORD-025** ❌

The root cause is **a secondary, non-intersecting design gap in Phase 13.2.2** — not a regression of the explicit entity isolation fix. It occurs under a specific precondition: the conversation must have an **active `order_id` from a prior session turn** (e.g. Turn N was an order query). When the user then queries a product with an explicit ID (`"Tell me about PROD-002."`), the domain-aware slot update (`update_slots_domain_aware`) receives **MERGED entities** (both `product_id` and the still-present context `order_id`) and, because `order_id` is truthy in the merged dict, the `if new_order_id:` branch **re-writes** `active_product_id = None` and **preserves** `active_order_id = ORD-025`. The subsequent implicit follow-up (`"What is its price?"`) then finds only `order_id` in context slots.

No production code, test, database, or configuration was modified during this investigation.

## Exact Root Cause

### The Bug Lives in Phase 13.2.2's `update_slots_domain_aware()` — Wrong Input

**File**: `supporthub-ai-architecture/ai/context.py`  
**Method**: `ConversationContext.update_slots_domain_aware()`  
**Called from**: `supporthub-ai-architecture/ai/orchestrator.py` line 79 + structured route handler  

**File**: `supporthub-ai-architecture/ai/orchestrator.py`  
**Line 79**: `_explicit_entities = route_decision.intent.entities if route_decision.intent else {}`

The orchestrator assigns `_explicit_entities` from `route_decision.intent.entities`. But `IntentResult.entities` is the **MERGED** entity dictionary (context + explicit), not the explicit-only dictionary.

This is the design gap:

```
classify() computes:
  explicit_entities = {product_id: PROD-002}           ← from current query regex
  context_entities  = {order_id: ORD-025}              ← from context slots
  entities (merged) = {order_id: ORD-025, product_id: PROD-002}  ← stored in IntentResult.entities

orchestrator does:
  _explicit_entities = route_decision.intent.entities
                     = {order_id: ORD-025, product_id: PROD-002}  ← MERGED, NOT explicit!

update_slots_domain_aware({order_id: ORD-025, product_id: PROD-002}):
  new_product_id = PROD-002  → set active_product_id = PROD-002, clear order/return/refund
  new_order_id   = ORD-025   → set active_order_id = ORD-025, clear active_product_id → None!

Result:
  active_product_id = None    ← WRONG: product was cleared by order branch
  active_order_id   = ORD-025 ← WRONG: order persists despite product being the current domain
```

The `if new_product_id:` block correctly sets `active_product_id = PROD-002` and clears `active_order_id`. But then the `if new_order_id:` block (lines 126–131) immediately overwrites: sets `active_order_id = ORD-025` and clears `active_product_id = None`.

Both `if` blocks are independent (not `elif`), so both execute when both keys are non-null in the merged dict. The second block wins, leaving the context in the ORDER domain.

### Secondary Contributing Factor: Missing Separation Boundary Between `_explicit_entities` and `IntentResult.entities`

`IntentResult` stores **merged** entities for tool resolution. The orchestrator should pass **explicit-only** entities to `update_slots_domain_aware()`. It currently passes `route_decision.intent.entities` (merged). `classify()` computes `explicit_entities` internally but does not expose it on `IntentResult`.

## Recommended Remediation (For Future Implementation Phase)

`IntentResult` needs an `explicit_entities` field separate from the merged `entities`. The orchestrator should pass `route_decision.intent.explicit_entities` (if added) — or re-compute it from `intent_classifier.extract_entities(query)` — to `update_slots_domain_aware()` instead of the merged `route_decision.intent.entities`.

Two minimal approaches:

**Approach A**: Add `explicit_entities: Dict[str, Any]` field to `IntentResult` dataclass. Populate it in `IntentClassifier.classify()` before returning. The orchestrator then uses `route_decision.intent.explicit_entities` for domain-aware slot updates.

**Approach B**: The orchestrator calls `intent_classifier.extract_entities(query)` directly (already available as a public method) to get explicit-only entities for `update_slots_domain_aware()`, without touching `IntentResult`.

Both approaches ensure that only entities **explicitly present in the current query** are used for domain-isolation slot updates, while the merged `entities` dict continues to serve tool argument resolution.

**Files that would change in remediation**:
- `supporthub-ai-architecture/ai/intent.py` — add `explicit_entities` to `IntentResult` (Approach A)
- `supporthub-ai-architecture/ai/orchestrator.py` — use explicit-only entities for `update_slots_domain_aware()`

**Files that must NOT change**:
- `ai/router.py`
- `ai/tools.py`
- `ai/response.py`
- `ai/security.py`
- `ai/context.py` — `update_slots_domain_aware()` logic itself is correct; the input is wrong
- Any authentication, PostgreSQL, MySQL, or RAG code
