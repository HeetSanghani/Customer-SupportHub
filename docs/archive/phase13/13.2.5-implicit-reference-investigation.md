# Phase 13.2.5 — Implicit Contextual Reference Resolution Investigation

## 1. Executive Summary
This read-only investigation analyzed why implicit contextual reference queries (e.g., "What is its price?", "Is it available?") fail during multi-turn browser interactions following an order query (`ORD-025`) and a product query (`PROD-002`), incorrectly returning Order `ORD-025` details instead of Product `PROD-002` details.

The investigation confirmed that Phase 13.2.4 successfully fixed explicit entity isolation for `IntentClassifier.classify()`, but identified four critical architectural gaps in `LLMIntentClassifier`, `AIRouter`, and `AIOrchestrator` that cause `active_order_id` to remain active or prevent `active_product_id` from being persisted during implicit multi-turn interactions.

---

## 2. Identified Root Cause Pathways

### Pathway 1: `LLMIntentClassifier` Omits `explicit_entities`
In `ai/intent.py` (lines 435–443), `LLMIntentClassifier.classify()` constructs and returns an `IntentResult` without populating the `explicit_entities` parameter. Consequently:
- `IntentResult.explicit_entities` defaults to `{}` (empty dictionary).
- In `AIOrchestrator.process_message()`, `_explicit_entities = route_decision.intent.explicit_entities` evaluates to `{}`.
- `ConversationContext.update_slots_domain_aware(_explicit_entities)` sees `has_any_explicit = False` and returns early without persisting `active_product_id = PROD-002` or clearing `active_order_id = ORD-025`.

### Pathway 2: `AIRouter` and `LLMIntentClassifier` Hardcode Order Context Only
In `ai/router.py` (line 87), `AIRouter.route()` calls:
```python
intent = self.llm_classifier.classify(
    query=query,
    customer_id=customer_id or "GUEST",
    active_order_id=context_slots.get("order_id") if context_slots else None,
    use_llm=True
)
```
- `AIRouter` extracts `context_slots.get("order_id")` and discards `product_id`, `return_id`, and `refund_id`.
- `LLMIntentClassifier.classify()` signature only accepts `active_order_id`. `INTENT_CLASSIFICATION_PROMPT` has no slot for `active_product_id`.
- When `LLMIntentClassifier` falls back to `self.fallback.classify()` (e.g. on Gemini API 429 rate limit or error), it passes `context_slots={"active_order_id": active_order_id}`, completely omitting `product_id`.

### Pathway 3: `RAG` Route Bypass in `AIOrchestrator`
In `ai/orchestrator.py` (lines 113–130), queries routed to `RouteType.RAG` (e.g. "What is the return policy for PROD-002?") execute RAG retrieval and return immediately without calling `ctx.update_slots_domain_aware(_explicit_entities)`. `PROD-002` is never saved in context, leaving `ORD-025` active.

### Pathway 4: Absence of Formal Contextual Reference Resolver
There is no dedicated pronoun or implicit reference resolution engine in `supporthub-ai-architecture`. Implicit reference queries rely entirely on active slots in `ConversationContext`. When `active_order_id` is left in context due to Pathways 1, 2, or 3, implicit queries fall back to `active_order_id`.
